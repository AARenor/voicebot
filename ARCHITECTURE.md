# Voicebot for Spas and Hotels — Architecture (living doc)

Status: draft v0.3 — 2026-09-29 ~23:00 UTC. Re-confirmed live (no plan-breakers; +Chirp3-HD et-EE GA, +ElevenLabs per-1k table, +Groq per-model scoping, +prior-art clients). Update as decisions get validated.

Goal: an inbound phone voicebot on a real Estonian number that answers like a human receptionist and completes bookings — rooms for hotels, appointments for spas — not just answers FAQs. Integratable: one new PMS = one driver file, zero code changes per venue.

## 0. Hardest lesson first

Answer rate going 60% to 100% is not the metric guests judge. One operator report describes a hotel whose Google rating fell nearly half a star after an agent answered everything but resolved nothing: real requests (move a reservation, split a folio, late checkout) ended in transfers to a smaller front desk. Source: LinkedIn operator anecdote, 2026-04-11 — single property, directionally matched by vendor guidance.

Design rule: no workflow goes live until the bot completes it end to end against the real booking system. Map the top-10 guest workflows on paper first (late checkout is the classic number one).

## 2. Call flow (Estonian number, integratable)

Caller (+372) -> DIDHub EE DID ($2.50) / Twilio fallback -> LiveKit SIP (inbound `eu` pinned: `{sub}.eu.sip.livekit.cloud`, dispatch `call-*`) -> Pipecat pipeline (Silero VAD, per-language STT, dual-LLM tools, per-language TTS, barge-in/backchannels) -> caller; Stay/Slot adapter writes to PMS (Apaleo/Mews/Cloudbeds/Zenoti or demo doubles); transcript → Postgres; Langfuse Cloud EU traces (OTEL `enable_tracing/enable_metrics`); staff dashboard holds queue; SMS (Messente EE preferred over Twilio US DPA friction) confirm/remind/cancel-link.

Latency budget: user-stop → voice-start <500ms (turn <1.5s e2e). Stream LLM tokens → TTS sentence chunks + filler `Üks hetk, kontrollin…`. Endpointing 550ms finished / 1300ms dangling + backchannel filter + 8s cap. Groq: total = TTFT + decode + network; short prompts (input tokens drive TTFT).

## 3. Booking integrations (researched 2026-09-29, re-verified)

Hotels: Apaleo first (see §1 flow), Mews second (Distributor availability/pricing/create; `mews.com/products/api`), Cloudbeds third (MyAllocator/Marketplace; rooms nest under room types; ARI `getRatePlans detailedRates`; `developers.cloudbeds.com`). Rule: confirm per property that the contract includes write API (create/change/cancel, live availability, restrictions, rates, limits, auth lead time).

Spas: Zenoti (full API + webhooks; search guest → add service → create → reserve slot → confirm → collect payment; `docs.zenoti.com`). Booksy (partner public API, 96 endpoints, RSA auth, per-country hosts; partnership required; `docs.booksy.com` mirror 2026). Fresha: NO public API — `developers.fresha.com` partnership-gated; third-party scrapers exist but must not carry a business; gated apply-or-manual-confirm fallback. Timely salon API unverified (timely.com hits = time-tracking) — do not cite.

Estonia-local: Hotellinx (in-house PMS since 1992, `hotellinxbaltics.com`, reservations/cleaning/spa/restaurant). API status unknown — check during pilot discovery; many local independents may run it instead of Mews/Cloudbeds.

Pärnu market re-check (2026-09-30): BOUK is confirmed through current official-site links plus active non-demo API records at 10 Pärnu accommodation properties, but no major Pärnu spa-treatment operation is confirmed on BOUK. Major spa hotels checked use SALBOS; Hestia Strand uses D-EDGE. BOUK supports room + hourly-service inventory and advertises a 14-day full-feature trial; official API access must be verified in the trial. Full property-by-property evidence, stale/migrated exclusions, and safe pitch claims: [`docs/research/parnu-booking-systems.md`](docs/research/parnu-booking-systems.md).

Summer phone-demand model (2026-09-30): no public Pärnu missed-call logs exist. Statistics Estonia room counts combined with Revinate/Canary/Alveni hospitality benchmarks produce an explicitly low-confidence estimate of 3,581–7,163 missed booking-intent calls across Pärnu city accommodation properties in June–August (30% midpoint 5,372). Never present this as observed local data; methodology, all-call sensitivity, spa scenarios, and pilot measurement requirements are in the research note above.

Adapter pattern: `StayAdapter` (night inventory, rate plans, `minGuaranteeType`, `prePaymentGrossAmount` vs total) vs `SlotAdapter` (service×provider×slot lifecycle, Zenoti `booking_id`). Shared only auth/idempotency/confirmation envelope. One interface (`search_availability`, `hold`, `confirm`, `cancel`, `guest_lookup`) per vendor driver. Drivers must support write/change/cancel — read-only never ships. Price utterances require live `price_quote_id`, never embeddings.

## 4. Humane Estonian voice (re-verified 2026-09-29)

Primary ET Azure Anu (F) / Kert (M) — real neural ET, 0.5M free/mo. Free failover PocketTTS-ET (6 bundled M+F prompts, clone receptionist WAV, `--temperature 0.3`) then Piper `et_EE-news-medium` (listen to 4 HF sample MP3s, assign own names; Mari/Vesta names come from 3rd-party `kubataba/sayfable-models piper-et-v1` 2026-09-15, plausible-unverified). Research voices (TartuNLP TransformerTTS, `text-to-speech-worker` MIT Docker 19 stars 2025-11-10) are start points, not products. Launch humane on managed ET voices; cost-down to self-hosted after evals + 200-utterance ET WER test (dates/names/prices, ET/RU accents, spa noise). Humane = barge-in, backchannels, native prosody + quantity (sada/saada), fast turns, warm transfers with context. Never send ET to XTTS/Chatterbox/OpenAI primary (no/weak ET, accent risk).

## 5. Compliance (Estonia/EU)

EU AI Act Art.50: disclose "I'm an AI assistant" at start in caller's language (ET/EN/RU script + `operaator` fallback). Estonia effectively 2-party recording consent: announce recording + purpose + retention + opt-out, log affirmative consent. GDPR: EU hosting/data residency (LiveKit `eu` inbound note §1 outbound caveat; Langfuse Cloud EU pilot, self-host later; Messente EE over Twilio US DPA/SCC friction), 30-day auto-delete, access/deletion handling, DPIA for voice-biometric-adjacent data. Payments via PMS links/3DS + tokenize-first (Cloudbeds bans raw PAN; Mews `AmountToChargeOnConfirmation` + PciProxy; Apaleo Adyen Drop-in) — never card numbers on recorded line, no PAN in transcripts/logs/RAG (Langfuse PII scrub on). No secrets to third-party research services (`.env`, SIP/PMS keys never in repo).

## 8. Hackathon + business-integration lens

Demo that wins: a live phone call on the +372 DID where the bot completes a real booking in an Apaleo/Mews test property, then shows the reservation inside the PMS. Judges remember completed bookings, not diagrams. Keep a 60-second backup recording — live demos die on venue wifi.

Business integration surface (what makes a venue say yes): per-business config (name, voice, language, workflows, PMS credentials) with zero code changes; adapter SDK so a new PMS is one driver file; Mews Marketplace listing as distribution once the driver is proven; shadow mode as default onboarding (bot drafts, staff confirms) so no venue risks autonomous booking on day one; eval dashboard showing resolution rate per workflow as the sales artifact.

Hackathon scope cut: one language (Estonian first for EE pilot; English first only for generic hackathon), one PMS (Apaleo sandbox fastest, Mews sandbox coverage), three workflows (availability check, new booking, late checkout), one transfer path with context. Everything else is a slide.
